# Agent Hub × Speeding 版本路线图

状态：Draft v0.1

## 1. 规划原则

版本规划同时服务两个产品：

- **Agent Hub** 要逐步成为可独立运营的多 Agent 组织平台；
- **Speeding** 要尽快证明核心游戏体验，而不是等待平台所有功能完成。

因此采用“双轨、同门槛”发布：每个阶段既有 Hub 平台交付，也有 Speeding 的真实使用场景；
只有通过阶段退出标准，才进入下一版本。

优先级定义：

- **P0 阻塞**：不完成就无法形成可信 MVP，或继续开发会产生大规模返工；
- **P1 增强**：不阻塞首个 MVP，但决定下阶段是否具备可扩展性和故事厚度；
- **P2 产品化**：规模化、运营和完整体验需要，首个验证版本可以延后；
- **P3 储备**：有价值但尚未被真实场景证明，不提前平台化。

## 2. MVP 的严格定义

Speeding MVP 不是 30 天、40 个事件和 7–8 小时长局。首个 MVP 是一条 30–45 分钟、可以
从开局走到日终的完整游戏日：

```text
新建 Run
→ 初始化玩家、Agent、人格和世界状态
→ 晨报出现压力
→ 玩家调查/谈判/下令
→ Agent 给出不同意见并发生一次协作
→ CanonicalAction 进入确定性结算
→ 即时与延迟后果写入状态和事件
→ 人物关系或情绪变化
→ 日终新闻、状态快照和完整复盘
```

它必须包含：

- 两项不可同时满足的利益；
- 一项失败但继续推进的行动；
- 一个系统事件、一个路线事件、一个人物私事；
- 一次 Agent A→B→C 的异步协作；
- 一个压力时钟和一次承诺锁；
- 同一输入不会重复结算；
- 所有变化可以解释来源。

以下不属于首个 MVP：完整群组会议、通用投票引擎、全部认知与长期记忆、40 个事件、多人排行、
7–8 小时内容和第三方能力包市场。

## 3. 总版本图

| 版本 | 产品目标 | Agent Hub 交付 | Speeding 交付 | 退出门槛 |
|---|---|---|---|---|
| R0 架构基线 | 停止继续耦合 | 协议、边界、关系与人格基线 | 世界观、账本、游戏框架 | 文档和所有权明确 |
| R1 Foundation | 建立动态系统底座 | Run、State、Event 最小内核 | 状态 Schema 与空局初始化 | 双 Run 隔离、事件幂等 |
| R2 Playable MVP | 证明游戏可玩 | Prompt、ToolResult、多跳最小闭环 | 一个完整游戏日 | 30–45 分钟端到端可复盘 |
| R3 Organization Alpha | 证明多 Agent 组织价值 | 群组、频道、会议最小闭环 | 董事会/派系与 2 小时章节 | 一对多、多对多真实运行 |
| R4 Simulation Beta | 证明世界和人物会持续变化 | 认知、记忆、动态关系能力包 | 三路线、传播、Director、40+ 事件 | 2–3 小时稳定局、内容可配置 |
| R5 Product 1.0 | 独立运营与完整长局 | 工作流产品化、扩展管理、运营能力 | 7–8 小时、多结局、比较复盘 | 可部署、可运营、可升级 |

## 4. R0：架构基线（当前版本）

### 已完成

- [x] 人格模板库、版本和 Agent 选择；
- [x] 有向关系、双向独立边、关系类型和拓扑 UI；
- [x] Organization MCP 的一对一通信和关系查询；
- [x] 关系变化事件及基础审计；
- [x] Agent Hub 平台扩展协议；
- [x] Hub/能力包/Speeding 拆分方案；
- [x] Speeding 玩家动力、生命线和推进机制框架。

### R0 剩余 P0

- [ ] 中性化 Hub 内 `[SPEEDING 组织消息]` 等游戏文案；
- [ ] 将 `behavior_profile` 标注为兼容投影；
- [ ] 将固定关系 reducer 标记为内置规则来源；
- [ ] 建立扩展清单 JSON Schema；
- [ ] 完成 Run、状态、事件和仓库边界 ADR。

### 退出门槛

- Agent Hub 不安装 Speeding 时不出现游戏品牌或游戏字段；
- 新功能的表、API 和模块所有权能够唯一归类；
- 扩展清单可离线校验。

## 5. R1：Foundation

目标：建立最小通用运行底座，不制作复杂扩展市场。

### Agent Hub P0

- [ ] `runs`、`run_agents` 和 draft/running/paused/completed 状态；
- [ ] Run 绑定 Agent 及人格版本快照；
- [ ] 最小 `state_schemas`、`run_states`、`run_state_changes`；
- [ ] revision 乐观锁、idempotency key 和 Run 完成后冻结；
- [ ] 最小统一事件信封和 append-only `events`；
- [ ] correlation、causation、root 和稳定事件时间；
- [ ] 能力包静态注册和 Run 绑定，不做在线商店与第三方代码执行；
- [ ] 包、Schema 和规则版本写入 Run 快照；
- [ ] 状态与事件 REST API；
- [ ] 最小运行状态页和事件时间线。

### Speeding P0

- [ ] `com.speeding.world` 第一版 Schema；
- [ ] 玩家净值、控制、合规、稳定、社会信用的初始状态；
- [ ] 四条生存生命线的初始定义；
- [ ] 一键创建空白 Speeding Run；
- [ ] 同一个 Agent 在两局中的状态完全隔离。

### 明确延后

- 完整包安装 UI、签名和市场；
- 通用 reducer DSL；
- 群组、会议和投票；
- 长期记忆和完整传播系统。

### 退出门槛

自动化测试必须证明：

1. 同一 Agent 可以进入两个 Run；
2. 修改 Run A 不影响 Run B、Agent 本体和人格模板；
3. 同一 idempotency key 只能改变一次状态；
4. 已完成 Run 不能继续写入；
5. 旧 Run 锁定的版本不会随模板更新改变。

## 6. R2：Playable MVP

目标：交付一个真正可玩的完整游戏日。

### Agent Hub P0

- [ ] 标准 ToolResult：成功、成本、状态提议、事件和延迟执行时间；
- [ ] `proposal → validate → commit` 提交流程；
- [ ] Prompt Composer 最小阶段：身份、职责、人格、动态状态、关系、应用上下文；
- [ ] Prompt provenance 与渲染哈希；
- [ ] 因果链 hop、事件数、Token、工具次数和 wall-clock 预算；
- [ ] 异步同链路 A→B→C；
- [ ] 每一跳重新鉴权和收窄上下文；
- [ ] A→B→A 可回报，超限链路产生 guard 事件；
- [ ] 禁止同步互等，但不再禁止所有嵌套业务行为。

### Speeding P0

- [ ] 一个完整游戏日流程；
- [ ] 一个可结算 CanonicalAction 主链；
- [ ] 两项主要行动、一次调查和一次人物谈判；
- [ ] 三个压力时钟；
- [ ] 一次承诺锁；
- [ ] 一个系统、路线、人物私事事件；
- [ ] 一次即时结算和一次延迟结算；
- [ ] 一次 fail-forward；
- [ ] 最小人物情绪/关系变化；
- [ ] 晨报、命令面板、人物对话、日终新闻和复盘 UI；
- [ ] 规则失败时整回合不落账。

### 可以采用的临时限制

- 固定 3–4 名核心 Agent，不要求全部角色登场；
- 状态 Schema 和事件模板可以随 Speeding 代码发布；
- 情绪先使用 3–4 个固定字段，不建设通用人格心理编辑器；
- 会议先由一次受控的串行/并行 Agent 协作表达，不冒充完整群组产品；
- Director 先使用确定性触发规则，不需要自主大模型导演。

### 退出门槛

- 新玩家可以独立完成 30–45 分钟流程；
- 关键行动有至少两个不可兼得后果；
- Agent 意见确实改变信息、执行条件或结算，而不只是对白；
- 服务重启后可以继续；
- 从最终状态可以回放每个变化的行动、规则和 Agent 链路；
- 相同状态、seed 和 CanonicalAction 得到相同机械结算。

达到这里，才可以称为 **Speeding MVP**。

## 7. R3：Organization Alpha

目标：把 MVP 中验证过的协作升级为 Agent Hub 的独立产品能力。

### Agent Hub P1

- [ ] 群组和成员；
- [ ] leader、成员、观察员和外部来宾；
- [ ] 最小频道和订阅；
- [ ] fanout：全员、按角色、仅 leader；
- [ ] aggregation：全部回复、首个成功、leader 汇总；
- [ ] 最小会议、参与者和会议记录；
- [ ] Organization MCP 增加 group_send、channel_publish、meeting_start；
- [ ] 组织树、频道和会议记录 UI；
- [ ] 消息排队位置、耗时和失败原因。

### Speeding P1

- [ ] 正式董事会群组；
- [ ] 三个主要派系；
- [ ] 群组会议和私下游说；
- [ ] 一项需要多人协作的交易；
- [ ] 一次群体反对或组织夺权；
- [ ] 内容扩展至约 2 小时；
- [ ] 第一版路线锁定。

### 延后至 R5

- 通用可视化工作流设计器；
- 任意复杂投票、代理投票和多级审批；
- 嵌套组织和完整企业 IAM。

### 退出门槛

- 一对一、一对多、多对多均有真实 Agent 测试；
- 每个成员是否收到、是否处理、回复向谁可见都可审计；
- 群组不等于无脑广播；
- Hub 在没有 Speeding 的租户中可以独立创建和运行团队会议。

## 8. R4：Simulation Beta

目标：建立持续变化的人物与世界，并证明内容可以规模化生产。

### 通用能力包 P1

- [ ] `io.zerone.emotion`：动态情绪、衰减和阈值叙述；
- [ ] `io.zerone.belief`：知道、相信、怀疑、争议、遗忘；
- [ ] `io.zerone.subjective-memory`：主观解释、情绪、重要度和检索；
- [ ] `io.zerone.relationship-dynamics`：按 Run 隔离的信任、敌意、依赖；
- [ ] 可见性、跨租户、跨 Run 和提示词注入测试。

### Speeding P1

- [ ] 世界事实与 NPC 认知分离；
- [ ] 私聊、公告、媒体、监管和小道消息传播；
- [ ] 延迟、可信度、失真、泄漏和传播半径；
- [ ] 连续性、程序、去权力三条路线；
- [ ] 真相调查交叉轴；
- [ ] 自主派系议程和待办债务；
- [ ] 统一事件内容 Schema；
- [ ] 40 个以上系统/路线/人物/环境事件；
- [ ] 受规则约束的 Narrative Director；
- [ ] 内容版本和旧存档锁定。

### 退出门槛

- 未知事实不会进入 NPC 上下文；
- 不同 NPC 可以合理持有冲突认知；
- 人物关系会改变信息、执行、投票或工具可用性；
- 2–3 小时游戏中不存在明显重复最优行动；
- 内容人员可以不修改 Hub Core 添加事件和角色内容。

## 9. R5：Product 1.0

目标：Agent Hub 和 Speeding 都具备独立运营条件。

### Agent Hub P2

- [ ] 工作流版本、步骤运行、审批和投票；
- [ ] 会签、法定人数、否决、超时升级和成员快照；
- [ ] 可视化工作流管理；
- [ ] 完整能力包安装、权限审核、升级、禁用和卸载 UI；
- [ ] 包签名和发布制品；
- [ ] 运行配额、监控、告警、计费计量和租户运营；
- [ ] 数据保留、归档、导出和灾难恢复。

### Speeding P2

- [ ] 内容扩展至 7–8 小时；
- [ ] 多结局和三类遗产评价；
- [ ] 每日新局面；
- [ ] 多维排行、路线标签和玩家比较；
- [ ] 长局摘要和离线恢复；
- [ ] 新手引导、难度和可访问性；
- [ ] 内容运营、版本更新和旧存档兼容；
- [ ] 成本、延迟和 Agent 失败降级达到线上标准。

### 退出门槛

- 两个产品可以独立部署和升级；
- Speeding 不直连 Hub 数据库；
- 禁用 Speeding 不影响 Hub；
- Hub 至少有一个非 Speeding 的多 Agent 场景验证通用性；
- 长局成本、失败率、恢复和数据保留符合运营目标。

## 10. 优先级总表

### P0：现在到 MVP

1. Hub 边界清理；
2. Run 与 RunAgent；
3. 通用状态、revision 和历史；
4. 最小统一事件、幂等和因果链；
5. 静态能力包注册与 Run 版本锁；
6. ToolResult 和状态提交；
7. Prompt Composer；
8. 链路预算和异步 A→B→C；
9. Speeding 一个游戏日；
10. 压力时钟、承诺锁和最小确定性结算；
11. 三类事件和日终复盘。

### P1：MVP 后进入 Alpha/Beta

- 群组、频道和最小会议；
- 正式派系与两小时内容；
- 情绪、认知、记忆和动态关系能力包；
- 完整传播系统；
- 三条路线、真相轴、Director 和 40+ 事件。

### P2：进入 1.0

- 完整工作流、审批和投票；
- 能力包运营 UI、签名和升级；
- 7–8 小时长局；
- 排行、每日局面和内容运营；
- 监控、配额、计费、归档和恢复。

### P3：真实需求出现后再做

- 任意 JavaScript UI 插件；
- 通用游戏时钟引擎；
- 把压力时钟、承诺锁抽成平台标准；
- 复杂嵌套组织与全功能企业 IAM；
- 无真实第二场景验证的抽象能力包。

## 11. 版本推进规则

每个版本必须遵守：

1. **没有退出门槛通过记录，不进入下一版本。**
2. **每个 P0 功能必须有端到端验收，不以建表或 UI 出现为完成。**
3. **Speeding 功能不得通过新增 Hub 游戏字段实现。**
4. **先完成一条垂直链路，再横向增加角色、事件和页面。**
5. **新抽象至少需要当前真实场景和一个独立复用场景，只有 Speeding 使用的先留在 Speeding。**
6. **每次发布保存 Schema、规则、提示词和内容版本，旧 Run 必须可复盘。**

## 12. 接下来四个开发批次

### Batch 1：R0 收口

- 中性化组织消息；
- 标注兼容字段与内置 reducer；
- 扩展清单 Schema；
- 四份关键 ADR。

### Batch 2：R1 数据骨架

- Run/RunAgent；
- State Schema/RunState/StateChange；
- 双 Run 隔离和冻结测试。

### Batch 3：R1 事件与页面

- 最小 Event；
- 幂等和因果 ID；
- Run 状态页和时间线；
- Speeding 空局初始化。

### Batch 4：R2 端到端切片

- ToolResult、Prompt Composer、预算和 A→B→C；
- 一个 CanonicalAction；
- 三类事件、压力时钟、承诺锁、延迟结算与日终复盘。

完成 Batch 4 后进行第一次真实玩家测试，再决定优先进入群组协作还是加深世界模拟。
