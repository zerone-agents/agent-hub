# Agent Hub 主导的版本路线图

状态：Draft v0.2

## 1. 产品推进方式

当前只维护一条主开发路线：**持续迭代 Agent Hub，Speeding 作为贯穿始终的参考应用和验收案例**。

```text
Agent Hub 提出一项通用能力
        ↓
实现最小平台闭环
        ↓
用 Speeding 的真实人物/组织/世界场景测试
        ↓
用一个非游戏场景做反向验证
        ↓
通过后进入 Agent Hub 下一版本
```

这意味着：

- Agent Hub 的版本是正式版本主线；
- Speeding 不与 Hub 并列排另一条工程主线；
- Speeding 的需求用于发现平台缺口、形成验收案例和验证扩展协议；
- 只有 Speeding 需要的世界观、账本、剧情和玩家 UI 留在案例应用，不进入 Hub；
- 每项抽象必须同时经受 Speeding 和至少一个非游戏组织场景测试，防止平台被游戏反向定制。

## 2. 三类待办

### A. Agent Hub 产品待办

进入版本主线，必须具备通用 API、权限、审计、UI 和自动化测试。

### B. Speeding 验收案例

不作为独立平台功能排期。每个 Hub 版本选择一个最能暴露问题的 Speeding 场景，建立固定
fixture、Agent、关系、输入和预期结果。

### C. Speeding 内容需求池

世界观、路线、私人事件、结局和玩家体验继续研究，但不阻塞当前 Hub 版本。只有当某项内容
需要新的平台能力时，才把“能力缺口”抽象回 A 类待办。

## 3. 优先级

- **P0 当前版本阻塞项**：没有它，本版本的通用能力无法闭环或无法被真实 Agent 验证。
- **P1 下一版本候选项**：当前版本可以运行，但无法覆盖下一类多 Agent 协同。
- **P2 产品化项**：规模、运营、可视化和第三方使用需要。
- **Research 内容研究项**：继续设计和积累案例，不进入 Hub Core 实现。

每个版本只完成一组平台问题，不把后续所有 Speeding 需求提前塞进当前版本。

## 4. 统一验收模板

每项 Agent Hub 能力都必须回答五个问题：

1. **通用能力是什么？** 不使用 Speeding 领域词描述。
2. **Speeding 怎样使用？** 给出具体人物和事件链。
3. **非游戏怎样使用？** 给出企业、研究或客服场景。
4. **平台边界在哪里？** 哪些数据和规则仍由应用拥有。
5. **通过证据是什么？** API、真实 Agent 运行、审计记录和自动化测试缺一不可。

## 5. H0：平台边界收口（已完成）

目标：确保后续功能从一开始按平台方式建设。

### Agent Hub P0

- [ ] 将 `[SPEEDING 组织消息]` 改为中性平台消息信封；
- [ ] 搜索并清理 Hub 运行时代码里的其他游戏品牌和世界语义；
- [ ] 将 `behavior_profile` 标记为 deprecated compatibility projection；
- [ ] 将固定关系事件/分值标记为内置 `relationship-dynamics` 规则来源；
- [ ] 为 `extension.yaml` 建立 JSON Schema、校验器和有效/无效 fixtures；
- [ ] 建立四份 ADR：Run、状态所有权、事件语义、Hub/应用仓库边界；
- [ ] 明确模板、能力包、MCP 和垂直应用的不同权限。

### Speeding 验收案例

- 现有财务、法务、董事会和对手关系在中性化后仍能通信；
- 人格、关系类型和消息记录不丢失；
- Hub 页面不安装 Speeding 时不出现财富游戏字段。

### 非游戏反向案例

- 建立“研究主管 → 分析师 → 审核员”三 Agent fixture；
- 验证它使用同一关系和消息协议，不需要 Speeding 字段。

### 退出门槛

- 扩展清单可离线校验；
- Hub Runtime 不再输出 Speeding 品牌消息；
- 两套案例均通过现有一对一通信测试。

## 6. H1：Run 与通用状态

> 状态：已完成（2026-09-12）。实现、页面与 Speeding/非游戏双案例验收均已通过。

目标：让 Agent 在多个任务、推演或游戏中拥有互不污染的运行状态。

### Agent Hub P0

- [x] `runs` 与 draft/running/paused/completed/archived 状态机；
- [x] `run_agents`，保存参与者和 Agent 配置/人格快照引用；
- [x] 能力包静态注册、启用及 Run 显式绑定；
- [x] Run 锁定包、Schema、提示词和规则版本；
- [x] `state_schemas`、`run_states`、`run_state_changes`；
- [x] revision 乐观锁和 idempotency key；
- [x] Run 完成后冻结写入；
- [x] 状态初始化、读取、提交和历史 API；
- [x] 最小“运行详情 / Agent 状态 / 变化历史”声明式 UI。

当前不做：第三方代码执行、包市场、复杂 reducer DSL、游戏虚拟时钟。

### Speeding 验收案例

- 同一个财务 Agent 同时进入两局；
- 两局具有不同压力、信任和财富世界状态；
- 修改第一局不影响第二局、Agent 本体及人格模板；
- 游戏状态由 `com.speeding.world` Schema 声明，Hub Core 不新增财富字段。

### 非游戏反向案例

- 同一个分析师同时参加“市场研究”和“风险审查”两个 Run；
- 两个任务的进度、置信度和临时上下文互不污染。

### 退出门槛

- 双 Run 隔离、并发 revision、幂等、冻结和版本快照自动化测试通过；
- 两类状态均使用相同 API；
- 删除 Speeding Schema 后通用 Run 仍可运行。

## 7. H2：统一事件、工具结果与提示词合成

目标：让平台内所有变化可追踪、可恢复、可解释。

### Agent Hub P0

- [ ] 持久化统一事件信封；
- [ ] correlation、causation、root、scope、subject 和 idempotency；
- [ ] 至少一次投递、重试、超时、取消和死信；
- [ ] 同一 scope + subject 的稳定排序；
- [ ] 标准 ToolResult：结果、成本、状态提议、事件和延迟时间；
- [ ] `proposal → validate → commit` 状态提交；
- [ ] 最小声明式 reducer；
- [ ] Prompt Composer：身份、职责、人格、组织、动态状态、关系、应用上下文；
- [ ] 保存提示词 provenance、资源版本和渲染哈希；
- [ ] Run、Agent 和因果链的事件数、Token、工具次数及时间预算。

### Speeding 验收案例

- 玩家提出一项资产处置方案；
- Agent 只输出 CanonicalAction/状态提议；
- Speeding 规则结算后通过 Hub 提交事件和状态；
- 重复投递不会重复扣款；
- 延迟结果能够在未来时间点进入同一因果链；
- 日终能够解释每个数值变化来自哪个行动、规则和 Agent。

### 非游戏反向案例

- 分析师提交报告，审核工具返回修改意见，任务状态从 review 变为 approved；
- 重试不会重复创建审批记录，完整提示词来源可审计。

### 退出门槛

- 服务重启不丢已接受事件；
- 幂等、预算终止和旧版本回放测试通过；
- LLM 无法绕过提交协议直接修改最终状态。

## 8. H3：可控多跳协作

目标：解决真实的 Agent A→B→C、回报、越级和有限循环。

### Agent Hub P0

- [ ] `agent_messages` 接入统一事件因果链；
- [ ] conversation/root/parent、hop、deadline 和链路预算；
- [ ] 同步调用栈继续禁止互相等待；
- [ ] 异步链路允许接收方继续发送；
- [ ] 每一跳重新校验 relation、action、scope 和上下文；
- [ ] A→B→A 合法回报；
- [ ] A→B→A→B 由幂等和预算停止，不按人物身份永久禁止；
- [ ] 消息排队位置、耗时、失败和 guard 原因可见；
- [ ] Organization MCP 接受并返回链路字段。

### Speeding 验收案例

- 玩家让董事长制定方案；
- 董事长将财务部分交给财务 Agent；
- 财务 Agent 将法律风险咨询法务 Agent；
- 法务回报财务，财务汇总给董事长；
- “喜欢越级”的人格可以尝试直接报告玩家，但仍需关系权限允许；
- 恶意或错误循环在预算处有解释地停止。

### 非游戏反向案例

- 研究主管把数据任务交给分析师，分析师把结果交给审核员，审核员退回一次后通过。

### 退出门槛

- A→B、B→A、A→B→C、A→B→A 和预算终止均有真实 Agent 测试；
- 跨租户、无反向权限、越权上下文和同步死锁均被拒绝；
- 不依赖 Speeding 人格或世界字段。

完成 H3 后，Agent Hub 已具备第一版可对外验证的“多 Agent 协作运行平台”能力。

## 9. H4：群组、频道和会议

目标：从点对点关系进入一对多与多对多组织协同。

### Agent Hub P1

- [ ] `agent_groups`、`group_members` 和成员角色；
- [ ] leader、成员、观察员和外部来宾；
- [ ] 群组可见性、任期和成员变更审计；
- [ ] 频道、订阅和消息线程；
- [ ] fanout：全员、按角色、仅 leader、轮询；
- [ ] aggregation：全部回复、首个成功、leader 汇总；
- [ ] 回复可见性；
- [ ] 最小会议、参与者、议程和会议记录；
- [ ] group_send、channel_publish、meeting_start MCP 工具；
- [ ] 组织树、频道和历史会议 UI。

### Speeding 验收案例

- 董事会、连续性联盟、程序联盟和去权力联盟；
- 一次董事会会议、一次派系私聊和一次公告；
- 不同成员因关系、信息和人格产生不同回复；
- 能确认谁收到、谁处理、回复对谁可见。

### 非游戏反向案例

- 一个研究团队举行方案评审会，由组长汇总成员意见并形成纪要。

### 退出门槛

- 一对多、多对多真实 Agent 运行通过；
- 群组不是简单同步广播；
- Speeding 不存在时仍可独立使用团队和会议功能。

## 10. H5：工作流、审批与群体决策

目标：把偶发协作升级为可重复的组织流程。

### Agent Hub P1

- [ ] workflow/version/step/run 数据模型；
- [ ] 串行、并行、交接、会签和条件分支；
- [ ] approval、vote、quorum、veto 和 timeout escalation；
- [ ] 投票开始时冻结成员、角色和权重；
- [ ] 工作流输入输出 Schema、重试和补偿；
- [ ] workflow_start、approval_vote MCP 工具；
- [ ] 工作流及审批历史 UI。

### Speeding 验收案例

- 资产转让经过财务预演、法务审核、董事会表决和监管确认；
- 派系变化不能在投票进行中篡改权重；
- 超时会升级而不是静默卡死。

### 非游戏反向案例

- 内容发布经过作者、事实审核、法务和负责人批准。

### 退出门槛

- 串行、并行、会签、多数票、否决和超时升级均可解释重放；
- 工作流模板不含 Speeding 专属步骤类型。

## 11. H6：动态人物能力包

目标：验证扩展协议可以提供复杂但非 Core 必需的 Agent 行为能力。

### 通用能力包 P1

- [ ] `io.zerone.emotion`：情绪状态、衰减和阈值叙述；
- [ ] `io.zerone.belief`：知道、相信、怀疑、争议和遗忘；
- [ ] `io.zerone.subjective-memory`：主观解释、重要度和检索；
- [ ] `io.zerone.relationship-dynamics`：按 Run 隔离的定向态度；
- [ ] 人格底色 + 动态状态 + 对方关系 + 可见记忆的提示词合成；
- [ ] 敏感字段、跨 Run、跨租户和版本迁移测试。

### Speeding 验收案例

- 两个角色对同一丑闻拥有不同认知；
- 一次背叛分别改变情绪、记忆和定向关系；
- 关系变化真实影响信息、执行、会议或工具使用；
- 同一长期 Agent 在两局中形成不同经历。

### 非游戏反向案例

- 审核 Agent 只记得自己参与的任务历史，并根据经验证的合作记录调整协作建议。

### 退出门槛

- 未知事实不会被注入 Agent；
- 记忆和人格不能授予权限；
- 卸载能力包后 Hub Core 与组织协作仍正常。

## 12. H7：扩展与运营产品化

目标：让 Agent Hub 能够由第三方和多个租户长期使用。

### Agent Hub P2

- [ ] 能力包安装、权限审核、升级、禁用和卸载 UI；
- [ ] 包签名、发布制品、依赖解析和迁移；
- [ ] 声明式 UI 完整 renderer；
- [ ] 运行配额、监控、告警和计费计量；
- [ ] 数据保留、归档、导出和灾难恢复；
- [ ] 至少两个非 Speeding 的参考应用或组织模板。

### Speeding 验收案例

- Speeding 以标准包安装和绑定；
- 升级世界规则不改变旧 Run；
- 禁用或卸载 Speeding 后历史可读且 Hub 继续运行。

### 退出门槛

- Agent Hub 可在不部署 Speeding 服务的环境中独立销售和运行；
- 第三方包不能跨租户、越权或形成不可审计的私有状态。

## 13. Speeding 内容需求池（Research）

这些内容继续研究和制作原型，但不控制 Hub 版本顺序：

- 完整世界实体、制度和事实库；
- 行动资格、合法性、系统连续性、时间窗口四条生命线；
- 压力时钟、承诺锁、派系议程和待办债务；
- 连续性、程序、去权力三条路线和真相调查轴；
- 系统、路线、人物私事和环境事件；
- Narrative Director；
- 40 个以上事件及 2 小时内容测试；
- 7–8 小时长局、多结局和遗产评价；
- 每日新局面、玩家比较、排行和复盘；
- Speeding 独立前端、规则服务、内容服务和数据库。

处理规则：内容研究发现缺少“群组投票”时，把通用群体决策能力送入 H5；发现缺少“市场价格
冲击”时，留在 Speeding 世界规则，不送入 Hub。

## 14. 当前四个开发批次

### Batch 1：完成 H0

- 中性化平台运行时；
- 标注兼容字段和内置规则来源；
- 扩展清单 Schema 与校验器；
- 四份 ADR；
- Speeding 与研究团队两套回归 fixture。

### Batch 2：H1 数据闭环

- Run/RunAgent；
- StateSchema/RunState/StateChange；
- 版本快照、隔离、幂等和冻结；
- 最小状态 UI。

### Batch 3：H2 事件闭环

- Event、delivery 和因果链；
- ToolResult、状态提交和 Prompt Composer；
- 预算、恢复和复盘；
- 用 Speeding 资产提议和研究报告审批双案例验收。

### Batch 4：H3 多跳闭环

- 组织消息迁移到事件链；
- 异步 A→B→C、回报和有限循环；
- 两套真实 Agent 链路测试。

完成 Batch 4 后，再根据 Speeding 案例暴露的问题进入 H4 群组，避免同时铺开所有系统。

## 15. 明确暂缓

- 不先开发完整 Speeding 游戏再倒推 Hub；
- 不为 Speeding 单独复制一套 Agent、消息、状态和事件系统；
- 不因未来可能复用就提前把压力时钟做成 Hub Core；
- 不在 H1 阶段建设完整插件市场；
- 不在点对点链路未稳定前建设复杂会议与工作流；
- 不以“数据库表存在”作为完成，必须有 Speeding 和非游戏真实 Agent 双案例。
